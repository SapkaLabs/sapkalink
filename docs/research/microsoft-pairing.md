# Independent Link to Windows pairing: public evidence and gates

Research date: 19 October 2026. Question: [Assess public evidence for legitimate independent Link to Windows pairing](https://github.com/SapkaLabs/sapkalink/issues/3).

## Finding

**Independent-client pairing remains unverified.** The consulted Microsoft sources describe Windows user flows and a general connected-device transport. They do not establish how an independently registered Linux application can obtain the authorization and enrollment accepted by the existing Android Link to Windows app. This bounded review found no complete vendor-documented path for that requirement; it does not prove that no such path exists.

Treat authentication/client eligibility as a prerequisite to implementation. A working Microsoft sign-in, discoverable device, valid transport frame, or community pairing description would each answer only part of the question. None by itself demonstrates authorized independent enrollment, continuing access, or connected-camera compatibility.

## What the vendor documents establish

**Windows Mobile Devices:** M1 specifies Windows 11, Android 10+, Wi-Fi, and Link to Windows 1.23112.189+. The user enables PC access, adds a device, scans a PC QR code, and follows Android permission prompts. Features have individual toggles, including connected camera. This documents user control in a Windows experience; it supplies neither a Linux enrollment contract nor OAuth scope definitions. [M1](https://support.microsoft.com/en-au/windows/apps/phonelink/manage-mobile-devices-in-windows)

**Phone Link:** M2 describes the same Microsoft account on PC and Android, QR or manual-code pairing, and Android permission grants. Its Android requirements exclude work/school accounts. Already-account-linked phones can be selected and then approved on Android. The documented account association, pairing, and Android permission grant are therefore separate observable steps. The article does not identify a third-party application registration, eligible resource scopes, device certificate issuance contract, or Linux peer identity. [M2](https://support.microsoft.com/en-us/windows/apps/phonelink/phone-link-requirements-and-setup)

**Removal and reconnect:** M3 says removal disconnects PC cross-device experiences, but complete cleanup may require removing the device in both Windows surfaces, signing out of Link to Windows, and unpairing Bluetooth where applicable. It explicitly requires pairing again for a future connection. This is evidence of user-visible removal behavior, not a documented API guarantee about token invalidation timing, trust-certificate destruction, or all-device/global OAuth revocation. [M3](https://support.microsoft.com/topic/remove-a-device-in-the-phone-link-9382f770-b203-7e0e-c81e-18d4053cf4e5)

## MS-CDP is a separate evidence layer

The specification describes discovery, authentication, and message transport among devices. Setup creates a device key pair. Discovery includes network presence requests/responses and BLE advertisements. The prerequisites page requires web-service access for same-account device information and says both devices must be signed into the same Microsoft account to fully establish a channel. Those statements do not document how this project obtains the required account association or service-issued material. [C1](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cdp/f5a15c56-ac3a-48f9-8c51-07b2eadbe9b4), [C2](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cdp/26e3df35-fd0f-4275-8693-a55b1ef1e5d3)

Connection sequencing includes device authentication, optional user-device authentication, and authentication completion; failure drops the connection. Device authentication carries a self-signed device certificate, while user-device authentication carries a user-device certificate when policy requires it. A self-created device key is consequently insufficient evidence of accepted user identity or enrollment. Certificate fields specify an exchange, not independent-client eligibility or provisioning. [C3](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cdp/3bed908e-9d73-4b19-870b-8e3ac41b5628), [device certificate](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cdp/550ae733-a6d7-4681-a6c0-1915571592f9), [user-device certificate](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cdp/9d61d74f-ec84-4ea7-abd3-15a74b4a448a)

The common header delegates inner protocols and message types to each channel. Product Behavior names Windows products, without establishing current Android Link to Windows or Linux behavior. **Inference:** implementing the outer MS-CDP specification cannot establish that the existing Android app accepts this client, that YPP/DCG is equivalent to this transport, or that a connected-camera channel is available. Applicability must be demonstrated for an exact component/version/feature later. [C4](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cdp/00b14441-7879-483d-96e4-f21306296eab), [product scope](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cdp/007422e0-bd9d-4c22-abd1-b6819fc3d16d)

## What the unofficial YPP/DCG lead adds

U1's README explicitly calls its subject undocumented and version-sensitive, derived from canary builds, embedded schemas, and reported service observations. Its stated coverage includes enrollment, pairing, relay, clipboard, and telemetry; this is not a demonstrated connected-camera client. The consulted documents do not provide an independently reproduced result tied to the user's exact Android build. [U1 README](https://github.com/ZonD80/msft-phone-link-docs/blob/243a16673475aec66e93a494e8c66c89b61c4b23/README.md)

The protocol document describes account OAuth followed by device identity, enrollment, QR/PIN trust establishment, and relay setup. It also lists refresh/expiry and trust-management operations. These are useful hypotheses for where the authorization boundaries may lie; operation names do not establish usable permissions, revocation semantics, or eligibility for a newly registered app. Its example uses a first-party OAuth client, first-party application headers, and broad pairing permissions. Those identifiers and request recipes are deliberately not reproduced here. [U1 PROTOCOL, sections 3–9](https://github.com/ZonD80/msft-phone-link-docs/blob/243a16673475aec66e93a494e8c66c89b61c4b23/PROTOCOL.md)

The architecture document describes a desktop role enrolled as Windows and says the phone filters linkable computers by OS/client type. If accurate for a target build, honest Linux peer identification may be a blocking eligibility question. Copying first-party identities or representing this application as Windows Phone Link falls outside the project's boundaries. Relay reconnect/presence descriptions are not proof that a revoked peer can or should reconnect. [U1 ARCHITECTURE](https://github.com/ZonD80/msft-phone-link-docs/blob/243a16673475aec66e93a494e8c66c89b61c4b23/ARCHITECTURE.md)

## Registration, consent, and the missing bridge

Microsoft's general identity documentation supports registering an application with its own client ID and personal-account audience. Its desktop OAuth guidance describes authorization code with PKCE, registered redirects, resource scopes, and user consent. This establishes a general authentication approach; **it does not establish that DCG exposes an independently grantable resource scope or accepts such an app**. The v2 identity guidance cannot simply be substituted for U1's reported legacy MSA/DCG flow. [I1](https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-register-app), [I2](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)

| Question | Result for an independent Linux client | Required evidence |
| --- | --- | --- |
| Discovery | Partial: CDP discovery is specified; applicability to this Android feature is unknown. | Exact component/version and discoverable feature mapping. |
| App registration and authentication | Unresolved; generic Microsoft login is insufficient. | Vendor-documented or explicitly authorized own-client registration, audience, redirects, scopes, and service eligibility. |
| Consent and least privilege | Windows user controls documented; independent consent vocabulary unknown. | Separation of OAuth grant, account association, device trust, Android permissions, and feature approval; camera-only or minimal grant availability. |
| Enrollment/pairing | Windows QR/manual flows documented; independent enrollment unverified. | Fresh identity accepted under the project's own name and truthful Linux metadata, with explicit Android approval. |
| Reconnect and expiry | Community hypotheses only for the target stack. | Access/refresh/key lifetimes, reauthentication rules, recovery without importing existing credentials. |
| Revoke | Vendor UI cleanup documented; independent API and timing unknown. | Partner removal, local-secret deletion, refresh/trust invalidation, and observable denial after revocation. |
| Connected camera | Unresolved and separate from basic pairing. | Current camera authorization and channel contract, followed by authorized interoperability evidence. |

## Minimum next validation and stop conditions

The smallest next step is a **documentation/eligibility gate**, with no private-service traffic: identify a Microsoft-published integration route, or obtain explicit confirmation that an application registered and named by this project may enroll an honestly identified Linux peer. Record the supported account type, resource/permission identifiers, least-privilege consent, device-trust issuer, and revoke contract. Drafting that inquiry is possible; sending it requires separate authorization. An ordinary login-only test would not resolve this gate.

Only after that gate and separate implementation/runtime authorization should a minimal experiment use a fresh project-owned app identity and test account with the user's existing Android Link to Windows. Limit it to one device pair: show the independent client name and requested permissions; obtain explicit phone approval; verify one accepted pairing and reconnect; revoke through documented controls; verify reconnect is denied. Keep only redacted status, versions, and error classifications. Do not add messaging, clipboard, files, or camera as incidental tests. Basic pairing success would still leave camera interoperability unresolved.

Possible **no-go conditions under the present project constraints** are: only first-party/allowlisted clients can obtain required service access; honest Linux identity is rejected; the required route depends on copied credentials, first-party impersonation, bypass, or a replacement Android companion; consent cannot be constrained or explained sufficiently for the desired feature; or revocation cannot be made reliable. These are decision criteria, not observed service outcomes or legal conclusions. Missing public documentation alone means **unknown / hold**, not proven impossibility.

The issue remains open because independent authorization, enrollment eligibility, and current-build applicability are not resolved. This note is original planning prose with public source pointers; it includes no credentials, device identifiers, captures, proprietary code, implementation, or tested interoperability claim.
